## 6.3.2 Comparison between COD and OD

### 6.3.2.1 General information

The basic specifications and illustrations of Operational Domains (OD) and Current Operational Domains (COD) were provided in  [Section 6.1, "Conceptual Overview"](06_01_openodd_model.html#top-openodd-model-concept).
A COD represents an instantaneous measurement and an OD may represent an aggregation of multiple measurements.
For COD one `TEMPORAL_EXTENT` and one `SPATIAL_EXTENT` are required.

### 6.3.2.2 TemporalExtent specification

The `TEMPORAL_EXTENT` can represent intervals of two format types:

* Two-dates interval: `["2024-06-01 08:12:53.784", "2024-07-01 18:33:57.681"]`
* Different times within the same date: `"2024-06-01 [08:12:53.784, 18:33:57.681]"`

### 6.3.2.3 Class TemporalExtent

For COD it specifies a single point in time; for OD it can also specify a time range.

### 6.3.2.4 SpatialExtent specification

The `SPATIAL_EXTENT` is either a latitude-longitude pair, or a polygon or region specified using a shapefile.
Shapefiles can exist using multiple formats listed in [Section 6.4.5, "Geo-fenced service area specification"](06_04_openodd_modules.html#sec-geo-fenced-service-area-specification).

## 6.3.3 Basic COD/OD

### 6.3.3.1 Basic COD/OD specification

The basic COD/OD may be represented as a simple table structure.
Consider, for example, [Code 59](#code-example-basic-cod), a simple taxonomy which describes wind speed and levels of rain:

Code 59. Example basic taxonomy for a COD/OD (free-form notation)

```
TAXONOMY
    weather is                        # record
        wind_speed is float representing velocity
        rain_level is
            no_rain
            light_rain
            heavy_rain
```

A COD/OD consistent with this taxonomy could be described using [Table 43](#tab-complexexamplecodtable):

Table 43. Example CODs table


| # | TEMPORAL\_EXTENT | SPATIAL\_EXTENT | WIND\_SPEED; m/s | RAIN\_LEVEL |
| --- | --- | --- | --- | --- |
| 1 | "2024-06-01 08:12:53.784" | "48.0232 11.7153" | 6.214 | no\_rain |
| 3 | "2024-06-03 11:42:21.913" | "48.0232 11.7283" | 1.783 | light\_rain |
| 5 | "2024-06-05 11:42:21.913" | "48.0215 11.7153" | 0.000 | heavy\_rain |
| 7 | "2024-06-07 18:33:57.681" | "48.0208 11.7132" | 0.000 |  |

[Table 43](#tab-complexexamplecodtable) describes 4 weather measurements:

* Row 1 represents a wind speed of 6.214 m/s and no rain.
* Row 2 represents a wind speed of 1.783 m/s and light rain.
* Row 3 represents a wind speed of 0 m/s and heavy rain.
* Row 4 represents a wind speed of 0 m/s and no data for rain (missing data is valid).

In example [Code 59](#code-example-basic-cod) the module conditions can specifically indicate that `RAIN_LEVEL` is required using `EXCLUDE_OR RAIN_LEVEL unknown`.
See [Section 6.4.4, "Module details"](06_04_openodd_modules.html#sec-concept-modules-module-details) for details.

## 6.3.4 COD/OD with complex structures

### 6.3.4.1 TaxonomyConceptValues specification

An instance of class `COD/OD` may be associated with an arbitrary number of instances of `TaxonomyConceptValues`.
Each of these instances refers to an instance of class `Attribute`.
An `TaxonomyConceptValues` instance itself can be related to an arbitrary number of instances of one of the `` Record`s or `Attribute`s defined in the taxonomy, representing a measured value for this taxonomy concept.
And which type exactly is used is defined by the `Record `` or the type of the `Attribute` instance the `TaxonomyConceptValues` instance is referring to.

Consequently the COD/OD is represented by a array of arrays of values.
This suggests to use a tabular format (other formats are possible) as a simple way to represent a COD/OD for descriptions and examples in this document.
An array of values associated with a `TaxonomyConceptValues` instance represents a column in a table.
The entire COD/OD can be considered as an array of such columns, that is a table.

[Code 60](#code-example-cod-complex-structure) shows an example for a **Record** structure:

Code 60. Example COD with complex structure (free-form notation)

```
TAXONOMY
    weather is                                             # record
      rainfall_rate is float representing velocity         # attribute
      rainfall_type is                                     # categorical attribute
          dynamic                                          # categorical literal
          convective                                       # categorical literal
          orographic                                       # categorical literal
    intersection_features is                               # record
        refuge_island_count is an integer                  # numeric attribute
        number_of_ways is an integer representing count    # numeric attribute
        is_signalized is a boolean                         # boolean attribute
    intersection is                                        # record
        features is an intersection_features type          # attribute
        type is                                            # categorical attribute
            T_junction                                     # categorical literal
            Y_junction                                     # categorical literal
            X_junction                                     # categorical literal
```

The example [Code 61](#code-example-taxonomy-concept-value) shows a `TaxonomyConceptValues` instance, which points to the `Record` instance specifying the intersection, this `Record` instance is specified with a JSON format;
Other formats are possible.

Code 61. Example taxonomy concept value (JSON)

```
  {"intersection_features": {"refuge_island_count": 2, "number_of_ways": 3, "is_signalized": True}, "intersection_type": "T_junction"}
```

|  |  |
| --- | --- |
|  | When using JSON, missing values are not specified:  * A **Record** in which all values are missing is denoted as `{}`. * Missing values are simply omitted.   For example, a `features` with a value for `number_of_ways` and `is_signalized` but missing a `refuge_island_count` value is denoted as `{"number_of_ways": 4, "is_signalized": True}`. * The JSON representation does not provide typed value specifications. * JSON schema may be extracted from the Taxonomy and used for validating the structure of a JSON serialization when needed.  The following is not allowed and is considered an error:  * The library, that is used for interpreting the COD data, is not able to detect a "missing value code". |

## 6.3.6 OD aggregation of COD

In certain use cases, an OD may aggregate one or more CODs.
The aggregation rules are as follows:

* An instance of class `COD/OD` (OD) may compose zero or more instances of class `COD/OD` (COD).
* When an instance of class `COD/OD` (OD) aggregates one or more instances of class `COD/OD` (COD), the aggregation requirements are as follows:
* Every row in a COD is mapped to a single OD row, which means an OD row composes multiple COD rows, and no COD row is shared between two OD rows.
* The temporal extent of an OD row represents a time interval that is a union of all temporal extents of the COD rows that are mapped to it.
* The spatial extent of an OD row represents a polygon that is a union of all lat-long positions of all the COD rows that it is mapped to.
* For each OD row, the values of each OD cell are an aggregation of all corresponding cells in all COD rows that are mapped to it.

|  |  |
| --- | --- |
|  | * The n-th (COD) OD row is specified by the collection of all n-th items in the corresponding instances of `TaxonomyConceptValue` of which the **OD** (**COD**) is composed. * There may be multiple ODs, each of which aggregates multiple CODs. * Both ODs and CODs may be stored in multiple files. * A single COD file may be aggregated into multiple OD files. |
